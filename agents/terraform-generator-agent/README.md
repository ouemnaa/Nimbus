# Nimbus Terraform Generator Agent

Nimbus Terraform Generator Agent is an independent FastAPI service that converts the canonical architecture JSON produced by the Solution Architect Agent into organized Terraform files. The first useful target is a low-cost AWS development architecture consisting of a VPC, public and private subnets, an Internet Gateway, a NAT Gateway, an Application Load Balancer, ECS Fargate, PostgreSQL RDS, Secrets Manager, IAM, and CloudWatch Logs. The generator enforces two-AZ subnet coverage for the ALB and RDS subnet group based on AWS networking requirements [1] [2].

Terraform HCL is generated by deterministic Python renderers and Jinja2 templates. Optional LLM providers are isolated behind a provider abstraction for normalization assistance, error explanations, repair recommendations, and human-readable summaries. An LLM is never required for basic generation and is never the sole source of Terraform HCL.

## Supported input

The service reads only the canonical architecture fields required for generation: architecture identifiers and version, `cloud.provider`, `cloud.region`, resources, relationships, and each resource's identifier, name, provider type, category, scope, configuration, and dependencies. Markdown reports, Mermaid diagrams, natural-language sections, and diagram fields are intentionally ignored.

The supported logical AWS resource types are `aws_vpc`, `aws_subnet`, `aws_internet_gateway`, `aws_nat_gateway`, `aws_security_group`, `aws_lb`, `aws_ecs_cluster`, `aws_ecs_service`, `aws_db_instance`, `aws_secretsmanager_secret`, `aws_iam_role`, and `aws_cloudwatch_log_group`. CloudFormation-style `AWS::...` provider types are normalized into Terraform-style names. The generator also recognizes the implementation resources it derives, including EIPs, route tables and associations, ALB target groups and listeners, ECS task definitions, database subnet groups, generated passwords, and Secrets Manager versions.

## Generated file structure

| File | Responsibility |
| --- | --- |
| `versions.tf` | Terraform and AWS/random provider constraints. |
| `providers.tf` | AWS provider configured with `var.aws_region`; no credentials are generated. |
| `variables.tf` | Region, naming, ECS, database, network, and optional certificate inputs. |
| `locals.tf` | Normalized name prefix and common tags. |
| `networking.tf` | VPC, subnets, IGW, EIP, NAT, route tables, routes, and associations. |
| `security_groups.tf` | ALB, ECS, and RDS security groups. |
| `load_balancing.tf` | ALB, IP target group, and HTTP listener. |
| `iam.tf` | ECS execution role, managed policy attachment, and Secrets Manager read policy. |
| `observability.tf` | ECS CloudWatch log group. |
| `secrets.tf` | `random_password`, Secrets Manager secret, and secret version. |
| `database.tf` | Private PostgreSQL RDS and two-AZ DB subnet group. |
| `ecs.tf` | Fargate cluster, task definition, service, private networking, logs, and ALB registration. |
| `outputs.tf` | Network, ALB, ECS, RDS, and secret outputs. |
| `terraform.tfvars.example` | Safe examples only; no password or real secret. |
| `README.generated.md` | Architecture-specific run instructions, warnings, and repairs. |

The service never creates `terraform.tfvars`, state files, plan files, or `.terraform/` in the response. It may persist the generated response files under the configured `GENERATED_ARTIFACTS_DIR` for local development; that directory is ignored by Git.

## Deterministic repairs and derived resources

The repair layer makes only safe, deterministic changes. A fake NAT allocation ID such as `eip-alloc-123` is replaced with an `aws_eip` resource reference. An ALB with only one public subnet receives a second non-overlapping public subnet when the VPC CIDR allows it. An RDS instance with only one private subnet receives a second private subnet when possible. Missing ECS task definitions, target groups, listeners, execution roles, log groups, database subnet groups, generated passwords, and secret versions are derived as Terraform implementation resources and returned in `derived_resources` metadata.

Missing container images are represented by the required `container_image` variable rather than an invented image. Missing container ports default to port 80 with a warning. Missing database usernames default to the safe example `nimbus_admin`. Database passwords are always generated with `random_password` and stored through Secrets Manager. A missing ACM certificate produces an HTTP-only listener and a warning; no fake certificate ARN is created.

## Safety guarantees

The generator does not create AWS access keys, provider credentials, plaintext database passwords, public RDS instances, public ECS tasks, destructive lifecycle rules, or RDS ingress from `0.0.0.0/0`. The ALB may accept development HTTP traffic on port 80, and the response warns that HTTPS is not enabled. It also warns about a single NAT Gateway and single-AZ RDS because those are low-cost development defaults rather than highly available production designs.

The validator writes only validated relative paths into a temporary directory and invokes Terraform through subprocess argument arrays with `shell=False` and a timeout. It may run `terraform fmt -check`, `terraform init -backend=false`, `terraform validate`, and—only when both explicitly requested and globally enabled—`terraform plan`; the validation command follows Terraform's documented validation workflow [3].
It never runs `apply`, `destroy`, `import`, state commands, or `force-unlock`.
If Terraform is not installed, validation returns `SKIPPED` with an installation warning instead of crashing.

## API

### `GET /health`

Returns:

```json
{"status": "ok", "service": "terraform-generator-agent"}
```

### `POST /api/v1/terraform/generate`

The preferred wrapped request is:

```json
{
  "project_id": "optional-backend-project-id",
  "architecture_version_id": "optional-backend-version-id",
  "architecture_id": "dev-web-app-postgres",
  "architecture_version": "1.0.0",
  "architecture": {},
  "options": {
    "project_name": "nimbus",
    "environment": "dev",
    "aws_region": "us-east-1",
    "allow_repairs": true,
    "validate": false
  }
}
```

The endpoint also accepts the canonical architecture JSON directly. It returns `SUCCESS`, `NEEDS_INPUT`, `UNSUPPORTED`, or `FAILED`, along with generated files, supported and unsupported resources, derived implementation resources, repairs, warnings, next steps, and metadata.

### `POST /api/v1/terraform/validate`

Accepts a list of `{path, content}` file artifacts and validation options. The response contains `PASSED`, `FAILED`, or `SKIPPED`, plus each executed check, captured stdout/stderr, structured errors, and warnings.

### `POST /api/v1/terraform/generate-and-validate`

Returns both the generation response and the validator response in one object. Terraform plan remains opt-in and is additionally gated by `VALIDATION_ENABLE_TERRAFORM_PLAN=true`.

## Setup and run

```bash
cd agents/terraform-generator-agent
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload --host 0.0.0.0 --port 8002
```

On Windows, use `.venv\\Scripts\\activate` instead of `source .venv/bin/activate`.

A manual generation-and-validation request can use the fixture as follows:

```bash
python - <<'PY'
import json
from pathlib import Path
payload = {"architecture": json.loads(Path("tests/fixtures/ecs_rds_architecture.json").read_text()), "options": {"allow_repairs": True, "enable_plan": False}}
Path("/tmp/nimbus-terraform-request.json").write_text(json.dumps(payload))
PY
curl -X POST http://localhost:8002/api/v1/terraform/generate-and-validate \
  -H "Content-Type: application/json" \
  --data-binary @/tmp/nimbus-terraform-request.json
```

The service listens on port `8002` by default. Set `PYTHONPATH=.` when invoking from another working directory.

## Optional LLM providers

Set `LLM_PROVIDER=none` for deterministic-only operation. The supported values are `none`, `gemini`, `groq`, and `openrouter`. A selected provider requires its corresponding API key and model environment variables; keys are never returned to the frontend and are not logged. Basic Terraform generation continues to use controlled renderers regardless of provider configuration.

## Testing

```bash
pytest -q
```

The test suite covers generation, AWS type normalization, unsafe identifier handling, subnet and EIP repairs, missing container inputs, unsupported resources, safe artifact paths, missing Terraform CLI behavior, structured validation failures, forbidden command protection, API contracts, and the no-LLM path.

## Terraform installation

Install Terraform using the official distribution for the development machine, ensure the `terraform` executable is on `PATH`, and then rerun the validation endpoint. The generator itself does not install Terraform and does not require AWS credentials for generation or static validation. Provider downloads during `terraform init` may require network access.

## Current limitations and roadmap

The first implementation focuses on AWS ECS Fargate with an ALB and PostgreSQL RDS. HTTPS listeners with ACM certificates, path-based listener rules, multiple NAT Gateways, production backup policies, autoscaling, EKS, Lambda, DynamoDB, CloudFront, and other providers are not yet rendered. Future work should add resource renderers behind the same registry, more complete relationship-driven wiring, stricter architecture schema versioning, optional remote artifact storage, and a controlled explanation/recommendation workflow for configured LLM providers.
